# 00.1 — The Golden Rules (Read First)

> **Status:** Rules file. No code is produced from this MD — only understanding.
> **Audience:** Every AI session that touches this project.

---

## 🥇 The Four Golden Rules

These rules apply to every component MD in this folder. They are non-negotiable.

### Rule 1 — Clean Code Only

Every PHP file follows PSR-12 spirit:
- `camelCase` for functions and variables: `getUserById`, `$reservationCount`
- `UPPER_SNAKE_CASE` for constants: `DB_HOST`, `RESERVATION_OPEN_HOUR`
- `snake_case` for DB tables and columns: `menu_items`, `created_at`
- `snake_case` for filenames: `cancel_reservation.php`
- Functions are short — target ≤ 30 lines; split if longer.
- One function = one job. Name describes what it does.
- Type hints on parameters and return types where reasonable.
- Each function has a 1-line docblock explaining intent.
- Early returns instead of deep nesting.
- No copy-paste duplication.

### Rule 2 — Stay Inside The Spec

The current MD file is the entire scope.
- If the MD says "validate email", do not also add CAPTCHA.
- If the MD lists 5 fields, do not invent a 6th.
- If you (the AI) think something is missing, STOP and write a note. Do not add it silently.
- Out-of-scope features are listed in `00.4-SCOPE-BOUNDARIES.md`.

### Rule 3 — One Component At A Time

Each MD targets exactly one source file.
- Do not touch other source files while implementing the current MD.
- Do not pre-build files that are coming in later MDs.
- Finish the current component (including its health check) before moving on.

### Rule 4 — Health Check Is Mandatory

Every component MD ends with a Health Check section. The AI must:

1. Run `php -l` on every PHP file created.
2. Execute every test step listed.
3. Tick every checkbox.
4. If even one fails → fix it before reporting "done".

## 🔒 Security Rules (Apply Everywhere)

Independent of the current MD's scope:

| Rule | Why |
|------|-----|
| All SQL queries use `mysqli_prepare` + `bind_param`. **Zero string concatenation with user input.** | SQL injection prevention |
| All HTML output of dynamic data wrapped in `e($value)` (`htmlspecialchars`). | XSS prevention |
| Passwords: `password_hash()` on save, `password_verify()` on check. Never plain text. | Credential safety |
| Destructive actions (delete, cancel, update) require `POST` method. Check `currentMethod() === 'POST'`. | CSRF-lite + prevents accidental triggers |
| Pages requiring login call `requireLogin()` on the first non-include line. | Authorization |
| Admin pages call `requireAdmin()` on the first non-include line. | Privilege separation |
| Error messages are generic for login flows. Specific elsewhere. | Info leak prevention |
| `session_regenerate_id(true)` after a successful login. | Session fixation prevention |

## ❌ Forbidden Patterns

The AI must NEVER use these:

- `eval()`, `extract()`, `$$variable` (variable variables)
- `mysql_*` functions (deprecated; use `mysqli_*`)
- `SELECT *` in business queries (be explicit about columns)
- Inline `<style>` in PHP files (use `assets/css/style.css`)
- Output (echo / HTML) before `header()` or `session_start()`
- Composer / Laravel / Symfony / PDO / jQuery / React / Vue
- A closing `?>` at end of pure-PHP files (creates whitespace bugs)
- BOM in UTF-8 files
- Hardcoded paths like `C:\xampp\...`

## ✅ Communication Protocol With The Human

When implementing any MD:

1. **Confirm scope first:** "I am about to implement `[filename]` per `[MD-name]`. The scope is [one-line summary]. I will not modify any other file."
2. **Implement** following the skeleton in the MD.
3. **Run the health check** and report results: "Syntax: PASS. Test 1: PASS. Test 2: FAIL — fixing..." until all pass.
4. **Report done:** "Component `[filename]` complete. All health checks passed. Ready for next MD."

If anything is ambiguous in the MD, ask the human BEFORE writing code. Do not guess.
